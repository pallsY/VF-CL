# 40902 机会性第三通道：调度修订草案

## 决策经过与新边界

在读取任何开发准确率之前，逐项核对 manifest 与账本：167 项成功、2 项正在运行时，未启动的 14 项全部是 CIFAR-100 种子 70/72 的 `static`、`uniform` 和 `sample_only_off` 对照；核心 `drift` 项均已在 brf3080 的 RTX 3080 上完成。若系统性把余下对照交给 40902 的 RTX 4090，算法差值会与 GPU 型号及驱动差值重合，无法按原设计单独解释漂移调度贡献。既有调度修订还明确要求同主机、同型号 RTX 3080 与同驱动。基于此，最初决定不接入第三通道，且没有接入或追加任何作业。

用户随后明确要求继续提速。新的修订只允许在**逐项记录设备差异、保留原始 183 项全部结果，并把混合设备开发结果定位为筛选证据**的前提下，尝试机会性第三通道。它不能追认原协议的同设备保证；论文中的漂移调度优越性及三数据集第一主张仍须通过之后统一硬件口径的正式确认。不得在开发准确率上选择是否承认设备差异。接入前必须把此修订、代码、准入与原账本哈希外部锚定；任一关口失败即保持原双卡队列。

## 目的与硬边界

现有两条 RTX 3080 通道继续工作。40902 的 RTX 4090 只在环境与显存满足门槛时领取**尚未启动**的作业；它不可抢占或重复执行当前作业。混用不同 GPU 型号可能造成数值差异。每个启动事件必须记录主机、物理 GPU UUID、型号、驱动、Torch/CUDA 版本、共用进程及显存，并在结果报告中披露与按设备检查；不得把它说成与两张 3080 完全等价。

4090 的速度收益不是立项判据。若接入核验所花时间预计超过剩余队列时间，或会削弱配对比较，保留双卡队列并记录为未接入。

## 授权握手

冻结 worker 读取字典序最后一个 `QUEUE_LOCK_RESUME_*.json`，要求其中 PID 等于 worker 的直接父 PID；它还核验 manifest、生产提交、独占 plan 和完整 start 事件。单纯通过 SSH 启动远端 worker 必然不能通过。

中央协调器在 brf3080 持有原全局队列锁，是**唯一**待办认领者及 `ATTEMPTS.jsonl` 写入者。40902 broker 是冻结 worker 的直接父进程，只接收一个已认领 job key，不读取成绩、不决定重试、不写 ledger。两台服务器目前不能直接以批处理 SSH 相互登录；控制面因此使用结果根**之外**的独立 NFS 文件邮箱。当前已授权的 Windows 会话只负责启动并核对一次 40902 broker，后续队列运行不依赖该会话持续在线。邮箱中 ASSIGN、REPORT、GO、EXIT、心跳记录均独占创建或按序号原子替换，并 `fsync`，绑定 job key、manifest SHA、生产/调度提交及轮次；旧消息不可复用。每次远端启动的顺序：

40902 的可领键在交接准备时由**当时未启动**的键按固定规则确定并写入外部锚点：先取尚未启动的 `sample_only_off/none/70`、`/72`；然后按 α=0.25、0.5、1.0，种子 70、72 的顺序把同 α、同种子的 `static`+`uniform` 完整二元组**纳入白名单**；最多四个键，白名单选择时不拆一对。若该四键不足则按实际数量。40902 只领这些键；本地两卡先领其余键，在其余键全部认领后可领取尚未被 40902 认领的锚定键，防止第三卡不可用拖住整队列。回退可能使白名单二元组最终分到不同设备；逐作业记录并在结果中明确标出，跨设备差值只作开发筛选。所有认领只按清单、可用性和上述固定次序，不读取准确率。

1. 中央写 ASSIGN；远端 broker 报告其真实 PID、主机、环境和 GPU 快照并等待 GO；中央核对远端生产副本干净且提交、manifest、挂载、GPU UUID、显存和外部进程记录符合锚点。机会性准入暂定为 4090 的 `memory.free` 连续 120 秒至少 6144 MiB，发 GO 前再查一次；可与外部任务共享，利用率及外部 PID 只记录不设硬门槛。显存不足时只跳过该通道，不占用 job key。
2. 中央阻止**所有**新本地启动及**全部** ledger 追加。已运行的本地 worker 可以完成计算，但其 finish 事件必须排队等候，不得在授权窗口中追加。全局写屏障一直覆盖远端授权读取。
3. 中央以独占创建写入远端 broker PID 的新 `QUEUE_LOCK_RESUME_NN.json`，再独占创建该 job 的 `attempt-01.plan.json`，追加完整 start 事件并 `fsync`；随后从 40902 再读并核对三者哈希与内容。锁序号必须保持两位数且小于 100，避免冻结代码的字典序最新锁问题。
4. 中央写 GO；broker 先从 40902 重新读取并核对最新 PID 锁、独占 plan 与完整 start 事件，同时再查 GPU，然后才作为直接父进程启动冻结 worker。中央等待该 attempt 新生成的 `APPROVED_CONFIG.json` 与 `JOB_RUNTIME.json` **内容完整且一致**，核对 job key、manifest/配置哈希、生产提交及 broker 新鲜心跳。这两个文件只有通过授权后才写出，作为授权 ACK；仅看到文件存在或 GO 被读取均不算 ACK。
5. ACK 通过后，中央追加恢复本地协调器 PID 的新锁记录，释放 ledger 写屏障与本地启动屏障。远端继续训练。远端退出后，中央核验 `JOB_SUCCESS.json` 和既有审计门，再写唯一 finish 事件。

反向切换同理：本地新 worker 启动后，中央必须等它写出授权后的配置/运行记录，才允许下一次切到远端 PID 锁；否则本地 worker 可能尚未读取本地锁就遭到切换。该等待也覆盖全部 ledger 追加。

任何 broker 心跳过期、ACK 缺失或含混、文件可见性不一致、GPU 准入失败、重复目录、编号越界、审计失败均停止新认领并保留全部证据。**不得以超时为由恢复锁、重发同一个 key 或删除 attempt。** 若已启动远端 worker，先核对其实际存活和结果，再按原 fail-stop 协议处理。

本修订只支持从尚未用过 40902 的原双卡队列做**首次**交接。若结果根已出现 `MULTIHOST_HANDOFF` 记录或远端授权锁，新协调器必须在恢复/追加账本前拒绝再次自动启动；中央异常退出后，本地 `/proc` 无法证明 40902 的 broker 或 worker 已停止。后续恢复必须先在 40902 核实进程与 EXIT/STOP、封存 ledger 和输出，再另写外部锚定的恢复协议。
